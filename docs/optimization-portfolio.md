# SPOT 성능 개선 기술 기록

프로젝트 전체 소개는 [SPOT 프로젝트 포트폴리오](SPOT-project-portfolio.md)를 참고한다. 이 문서는 성능 개선 사례의 근거를 보관하는 부록이다.

작성일: 2026-09-09
기준 커밋: `2e46837ecdd872782aae716a3c0301919ea04072`

## 프로젝트와 작업 범위

SPOT은 React Native·Expo·TypeScript·Zustand 기반의 장소 저장·탐색 앱이다. 지도와 장소 목록, 친구 관계, Instagram 공유 분석 결과, 광고 보상 및 알림을 연결한다. iOS Share Extension과 앱 사이에는 Swift 브리지와 App Group 저장소가 있다.

이번 작업에서는 저장소의 기존 추적 소스 148개(TS/TSX/Swift/Objective-C/Kotlin/Java)를 대상으로 구조와 호출 패턴을 정적으로 조사했다. 화면 19개, 컴포넌트 52개, 스토어 12개, 훅 6개를 포함한다. 의존성·생성 빌드 산출물은 직접 개선 대상에서 제외했다. 호출 경로를 직접 검토하고 변경한 부분은 지도/저장 장소 조회, 위치 조회, 검색 생명주기, 북마크 상태, 사진 정규화, API 로그다. 모든 기능을 실제 기기에서 실행했다는 의미는 아니다.

화면 TSX, JSX, 스타일, 이미지, 네이티브 코드에는 변경이 없다. UI 구성을 유지하면서 데이터 계층과 훅을 개선했다.

## 재현 가능한 수치

아래 수치는 **기준 커밋과 수정 코드의 실제 모듈을 Node에서 실행하되 HTTP와 GPS를 모의 구현으로 대체한 결과**다. 실행 시간, 실기기 FPS, 배터리, 서버 비용을 측정한 수치가 아니다.

| 항목 | 재현 조건 | 변경 전 | 변경 후 | 감소율 |
| --- | --- | ---: | ---: | ---: |
| 저장 장소 HTTP 호출 | 같은 좌표의 지도 핀과 목록 동시 요청 | 2회 | 1회 | 50% |
| 위치 권한 요청 | 초기 권한 미확정 상태에서 위치 조회 3개 동시 실행 | 3회 | 1회 | 66.7% |
| 현재 위치 GPS 조회 | 위치 조회 3개 동시 실행 | 3회 | 1회 | 66.7% |
| 인기 장소 스토어 변경 알림 | 1,000개 목록에서 같은 북마크 값 100회 적용 | 100회 | 0회 | 100% |

측정 원본: [optimization-metrics.json](optimization-metrics.json)
측정 코드: [benchmark-optimizations.cjs](../scripts/benchmark-optimizations.cjs)

독립적으로 완료된 요청, 서로 다른 좌표, 다른 로그인 토큰, 다른 저장 변경 revision은 공유하지 않는다. 따라서 일반적인 앱 사용 전체에서 항상 위 감소율이 나오는 것은 아니다. 특히 일부 목록 호출은 원본 좌표를, 지도 훅은 반올림 좌표를 사용하므로 좌표가 정확히 일치하지 않으면 요청을 합치지 않는다.

추가로 확인 가능한 코드 변화:

- API 계층의 로그 15개를 개발 모드 조건 내부로 이동하고, 중복 저장 장소 응답 로그 1개를 제거했다. 인기 장소 로그의 배열 변환과 JSON 직렬화도 프로덕션에서는 실행하지 않는다.
- 사진 정규화 구현 2개를 공통 함수 1개로 통합했다. 기존 `flatMap → filter → map → filter`의 4단계 배열 처리를 한 번의 순회로 변경했다. 시간 복잡도는 전후 모두 O(n)이며, 배열 처리 단계와 중간 배열을 줄인 개선이다.
- 기존 테스트 파일 6개를 포함한 테스트 18개가 통과했다. 추가된 회귀 테스트는 12개다.

## 문제 → 해결 → 검증

### 1. 지도와 목록의 중복 네트워크 요청

지도 핀용 `fetchMapPlaces`와 목록용 `fetchMyNewSavedPlaces`가 같은 `/main/me/places`를 별도로 호출했다. 두 호출의 응답 표현은 달라도 원본 데이터는 같았다.

`createSingleFlight`로 진행 중인 Promise만 공유하고, 각 호출자의 기존 매핑은 유지했다. 키는 로그인 토큰·정확한 좌표·저장 변경 revision으로 구성했다. 성공하거나 실패하면 공유 목록에서 제거하므로 이후 새로고침이 실패 결과나 오래된 완료 응답을 재사용하지 않는다.

검증: 동시 요청 2→1회, 키 분리, 완료 후 재조회, 실패/동기 예외 후 재시도, 지도와 목록의 반환 형태 확인.

### 2. 중복 위치 조회와 불필요한 상태 변경

여러 진입 경로에서 `refreshOnce`가 겹치면 권한 요청과 GPS 조회도 겹쳤다. 진행 중인 권한 요청과 위치 조회를 각각 공유했다. 같은 좌표를 다시 받아도 스토어에 새 좌표 객체를 넣지 않도록 했다. 위치 정확도 옵션과 새 요청 시 실제 위치를 읽는 동작은 유지했다.

검증: 동시 3회 호출에서 권한/GPS 각 1회, 권한 거부 시 GPS 미호출, 실패 후 재시도, 동일 좌표 객체 참조 유지.

### 3. 북마크 상태가 같아도 발생하던 목록 교체

기존 인기 장소 스토어는 북마크 값이 이미 같거나 대상이 없어도 전체 배열을 새로 만들어 구독자에게 변경을 알렸다. 저장 장소 스토어에도 유사한 불필요한 갱신이 있었다.

실제로 달라지는 항목을 찾았을 때만 배열을 복사한다. 변경이 없으면 기존 스토어 상태를 그대로 반환하고, 변경하지 않은 항목의 참조도 유지한다. 저장 장소의 언북마크 항목은 기존처럼 새로고침 전까지 목록에 남고, 신규 저장 항목은 맨 앞에 추가된다.

검증: 100회 동일 상태 적용에서 알림 0회, 실제 변경 시 알림 1회, 다른 항목의 참조 유지, 입력 객체 불변성, 신규 저장 동작.

주의: 여기서 측정한 것은 **Zustand 구독 알림 횟수**다. 실제 React 렌더링 횟수나 FPS로 표현하면 안 된다.

### 4. 취소·재진입과 오래된 검색 응답

지도/저장 목록 훅이 요청 시작 시점에 완료 키를 기록해, 요청 중 화면 이탈 또는 effect 재실행 후 같은 요청을 건너뛸 수 있었다. 성공적으로 활성 화면에 반영한 시점에만 키를 기록하도록 변경했다.

장소 검색은 훅이 소유하는 AbortController를 API까지 전달하고 cleanup에서 취소한다. 최근 장소/친구 검색 스토어는 현재 요청의 응답과 종료 처리만 반영한다. 이전 요청의 종료가 새 요청의 로딩을 먼저 끄거나 오래된 결과를 덮어쓰지 못하게 했다.

검증: effect setup/cleanup 재실행, 조회 중 blur 후 refocus, 검색 transport signal 취소, 늦은 검색 결과 미반영, 이전 요청 종료 중 새 요청의 로딩 유지. 훅 테스트는 생명주기 콜백을 모의 실행하며 React Native 렌더러 통합 테스트는 아니다.

## 이력서 문장 예시

아래 문장은 이번 변경에 대한 실제 기여와 측정 조건에 맞춰 사용할 수 있다.

- React Native 장소 탐색 앱의 지도·목록 조회 경로에 진행 중 요청 공유를 적용해, 동일 좌표 동시 조회 테스트에서 HTTP 호출을 2회에서 1회로 50% 절감.
- Zustand 북마크 갱신 시 불변 참조를 유지하도록 개선해, 1,000개 목록에 동일 상태를 100회 적용하는 테스트에서 불필요한 스토어 알림을 100회에서 0회로 제거.
- 위치 조회의 동시 실행을 통합해 모의 GPS 테스트에서 3개 호출을 1개로 축소하고, 검색 취소 및 화면 재진입의 비동기 상태 충돌을 회귀 테스트로 검증.

분량이 짧은 이력서에는 첫 번째 문장만 사용하고, 포트폴리오에서 두 번째와 세 번째의 조건·증거를 설명하면 된다. 앱 전체 속도 50% 향상, 배터리 66.7% 절감, 사용자 이탈률 감소처럼 측정하지 않은 효과로 바꾸지 않는다.

## 추가 성능 측정 후보

현재 개선 결과와 다음 조사 후보를 구분한다.

- 저장/인기 장소 목록은 부모 스크롤 안에서 `map`으로 렌더링한다. 데이터가 커질 때 가상화 효과를 검토하되, 바텀시트 제스처·광고·스크롤 위치의 UI 검증이 먼저 필요하다.
- 원본 좌표와 반올림 좌표 사용 정책을 통일하면 추가 중복을 줄일 가능성이 있다. 표시 거리·조회 범위의 요구사항 확인이 필요하다.
- 실제 기기에서 지도 진입·탭 전환·장소 저장·검색 취소를 반복하고 요청 수, React commit 수, JS 프레임 시간을 측정한다. iOS 공유 확장과 광고 SDK의 동작도 기기에서 별도 검증한다.
- 인기 장소 페이지네이션과 새로고침의 응답 순서, 프로필 조회의 요청 중복은 후속 검증 후보다. 이번 수치에 포함하지 않았다.
